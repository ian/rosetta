# Getting translations into your repo

`rosetta push` updates translation files on disk. Rosetta doesn't prescribe how
those changes reach your default branch, so pick the workflow that fits your team,
or combine several. All of them use the same `.rosetta/` config and lockfile.

| Workflow | Best for | API key in CI? |
| --- | --- | --- |
| [Local or agent](#1-local-or-agent) | Solo developers, coding agents, small teams | No |
| [Check-only gate](#2-check-only-gate) | Any team; pairs with every other workflow | No |
| [Pull request bot](#3-pull-request-bot) | Teams that review translations like code | Yes |
| [Commit to the branch](#4-commit-to-the-branch) | Teams that want translations live on merge | Yes |

## 1. Local or agent

Whoever changes the English runs `rosetta push` and commits the translations in
the same change. There's no bot, and CI runs on the translations like any other
commit.

```bash
export ROSETTA_API_KEY=sk-or-...
npx rosetta push
git add -A && git commit -m "Add billing copy"
```

For coding agents, the CLI is built to be driven programmatically:

- `rosetta status --json` shows what would change, without calling a model.
- `rosetta push --json` returns per-locale results and any failing keys.
- Exit codes are stable: 0 ok, 1 some locales failed, 2 usage/config error, 3 stale.
- It never prompts when not attached to a TTY. Destructive operations need `--yes`.

A line worth adding to your `AGENTS.md`:

> Translations are generated by Rosetta. Edit only the source locale files, then run
> `npx rosetta push` and commit the results. Never hand-edit other locales unless you
> mean to (hand edits are kept until the English changes).

## 2. Check-only gate

Run `rosetta check` on every pull request. It fails when a translation is stale,
missing, untracked, has extra keys, or has broken placeholders, ICU, or tags. It
never calls a model, so it needs no secret and works on forks.

```yaml
# .github/workflows/i18n-check.yml
name: i18n check
on: pull_request
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ian/rosetta@v1
        with:
          mode: check
```

Without the Action: `npx --yes rosetta-i18n@1 check`.

## 3. Pull request bot

After changes land on `main`, the Action runs `rosetta push` and creates or updates
one rolling pull request (branch `rosetta/translations`). Review it, then merge.
Later runs update the same PR instead of opening new ones.

```yaml
# .github/workflows/i18n.yml
name: i18n
on:
  push:
    branches: [main]
    paths: ["messages/en.json", ".rosetta/**"]   # your source files + config
  workflow_dispatch:
permissions:
  contents: write
  pull-requests: write
concurrency: { group: i18n, cancel-in-progress: false }
jobs:
  translate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/create-github-app-token@v1   # see "Tokens" below
        id: app
        with:
          app-id: ${{ vars.I18N_APP_ID }}
          private-key: ${{ secrets.I18N_APP_PRIVATE_KEY }}
      - uses: actions/checkout@v4
        with:
          token: ${{ steps.app.outputs.token }}
      - uses: ian/rosetta@v1
        with:
          mode: pull-request
          token: ${{ steps.app.outputs.token }}
        env:
          ROSETTA_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
```

## 4. Commit to the branch

The Action commits translations straight to the branch that triggered it. If the
branch moved in the meantime, it rebases and retries (up to 3 times).

On `main`, translations are live on the next deploy:

```yaml
on:
  push:
    branches: [main]
    paths: ["messages/en.json", ".rosetta/**"]
permissions:
  contents: write
jobs:
  translate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          token: ${{ secrets.I18N_TOKEN }}   # needed if main is protected, or if CI must run on the commit
      - uses: ian/rosetta@v1
        with:
          mode: commit
          token: ${{ secrets.I18N_TOKEN }}
        env:
          ROSETTA_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
```

On a pull request, translations ride along with the English change. Check out the
PR branch (not the default merge commit), because pushing needs a real branch:

```yaml
on: pull_request
jobs:
  translate:
    if: github.event.pull_request.head.repo.full_name == github.repository  # no secrets on forks
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.head_ref }}
      - uses: ian/rosetta@v1
        with:
          mode: commit
        env:
          ROSETTA_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
```

## Action reference

| Input | Default | Description |
| --- | --- | --- |
| `mode` | `pull-request` | `pull-request`, `commit`, or `check`. |
| `token` | `github.token` | Used to push and to open PRs. |
| `branch` | `rosetta/translations` | Rolling PR branch (`pull-request` mode). |
| `base` | triggering branch | PR base branch. |
| `commit-message` | `chore(i18n): update translations` | |
| `pr-title` | `chore(i18n): update translations` | |
| `pr-body` | `""` | Markdown placed above the generated summary. |
| `args` | `""` | Extra `rosetta push` arguments, e.g. `--locale es --key "auth.*"`. |
| `working-directory` | `.` | Directory containing `.rosetta/`. |
| `version` | auto | rosetta-i18n version or tarball. By default the Action uses the project's installed `rosetta` if there is one. Otherwise it uses the version matching the Action ref: `@v1.2.3` → `1.2.3`, `@v1` → latest `1.x`. |
| `node-version` | `22` | Node to set up. Pass `""` to use the runner's own Node. |

| Output | Description |
| --- | --- |
| `changed` | `"true"` if translation files changed. |
| `pr-url` | URL of the created or updated PR. |
| `commit-sha` | SHA of the translation commit. |

Behavior:

- **Only translation files are staged**: the target files `push` wrote, plus
  `.rosetta/lock.json`. Unrelated changes in the working tree are left alone.
- **Partial failures still land the locales that succeeded.** Failed locales are
  left untouched and listed in the PR body and job summary, and the step exits 1 so
  you notice.
- **Config and usage errors** (for example a missing API key) fail the step with
  exit 2 and change nothing.
- A **job summary** with per-locale counts and token usage is written on every run.

## Tokens

GitHub doesn't start other workflows for pushes or pull requests made with the
default `GITHUB_TOKEN`. That's fine for a direct commit to `main` if nothing needs
to run on it. You need a different token when:

- your CI (tests, required status checks) must run on the translation PR or commit;
- a protected branch rejects `GITHUB_TOKEN` pushes;
- a deploy workflow is triggered by pushes to `main`.

Use a **GitHub App token** (recommended: scoped, short-lived, and not tied to a
person) via [`actions/create-github-app-token`](https://github.com/actions/create-github-app-token),
or a fine-grained PAT with `contents: write` and `pull-requests: write`. Pass the
same token to both `actions/checkout` and the Action's `token` input.

If you can't use either, a fallback is to have the bot push a branch, run your CI on
it with `workflow_dispatch` (which works with `GITHUB_TOKEN`), wait for it to pass,
and then push the tested commit to `main`. It's more moving parts; prefer an App
token when you can.

## Costs and safety

- Only new, changed, or broken strings are sent to the model. Run
  `rosetta push --estimate` to see key counts and a rough token estimate first.
- Nothing is written for a locale unless every one of its keys passed validation.
- Keep the API key in CI secrets. `rosetta check` never needs it.
